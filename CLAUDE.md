# CLAUDE.md

Chrome MV3 extension for learning French while browsing. Vanilla JS, no build step, load unpacked.

Full feature list and roadmap: see `README.md`. Current phase and next tasks: see `TODO.md`.

## Conventions

- **Service worker owns state and all external calls.** Content script and side panel are UI only — never fetch APIs or hold canonical state. The one exception: `background/offscreen.js` runs the actual `Translator.*` calls, because that API requires a window context the service worker can't provide (see MV3 constraints below) — the service worker still owns the message contract and orchestrates it.
- **Bubble CSS is namespaced `.fla-*`** to avoid collisions with host pages.
- **The bubble is measured and re-placed after every content swap** (`placeBubble()`, duplicated in `content/content-script.js` and `pdf-viewer/bridge.js`) — "Translating…", a one-word gloss, and a paragraph's translation are wildly different sizes, so a position computed once at creation is wrong by the time there's content in it. It anchors below the selection by default, but moves *beside* it when the anchor is tall or the space below is thin, and clamps into the viewport as a last resort; `max-height: 60vh` + internal scroll in `content/popup.css` is what guarantees the action buttons stay on screen no matter how long the translation is.
- **Passage-length selections don't auto-translate.** At `DEFER_TRANSLATE_SEGMENTS` (4) lines-or-sentences the bubble renders a preview plus a 🌐 Translate button and waits — the common case for a long selection is wanting Practice, not a wall of translated text. The Translate button exists **only** in this deferred state; once translated the bubble is an ordinary one, and short selections never show it. Note the two copies of `segmentCount()` differ *deliberately*: a PDF text layer emits a `\n` per visual line, so `bridge.js` counts sentences where `content-script.js` counts lines first.
- **Reading-aid/toggle settings UI (`lib/settings-panel.js`) is a shared module between `popup.js` and `sidepanel.js`'s Settings tab** — both are regular extension pages (unlike content scripts, which can't import extension modules, hence `content/annotator.js` keeping its own `DEFAULT_COLORS`/`DEFAULT_CATEGORIES_ENABLED` copy), so this is a real shared module rather than a duplicated one. Both callers must provide the same element IDs in their HTML; `initSettingsPanel()` is idempotent (guards its own listener wiring) since the side panel's Settings tab can call it more than once per document lifetime, unlike the popup which is recreated fresh every open.
- **Every saved item stores context.** Never save a bare word — always with `contextSentence`, `sourceLang`, `url`, `savedAt`.
- **Vocab is keyed by URL**, not a flat array: `vocab[url] = [entries]`. Aggregate views are computed on demand.
- **SRS state lives on `cards`, keyed by lemma — never on vocab occurrences.** The same word saved from two pages is one card, not two. Each occurrence points at its card via `cardId`; each card tracks its occurrences via `occurrenceIds`. A due-review query scans `cards` (one entry per distinct word), never every URL bucket. `background/conjugation.js`'s `resolveLemma()` collapses verb forms onto their infinitive; anything it doesn't recognize falls back to its own lowercased (accent-preserved) surface form.
- **Bundled-data lookups (conjugation, lexicon) are background-owned.** `background/lexicon.js` mirrors `conjugation.js`'s shard-cache pattern for `data/lexicon/<letter>.json` + `data/cognates.json`. `saveWord()` fills `pos`/`gender`/`plural` from a lexicon lookup when the caller didn't supply them. `content/annotator.js` batches its per-page word list into one `LOOKUP_WORDS` message per scan rather than looking up bundled data itself, keeping that precedent — even though content scripts technically can fetch bundled extension resources directly.
- **Reading-aid config (`colorCoding`) is live across every open tab**, not just the active one — `content/annotator.js` reacts via `chrome.storage.onChanged` rather than the `SET_HOVER_MODE`-style "message the active tab" pattern used for interaction-mode toggles. Annotation always tags matched words with their computed classes at scan time; a class on `<html>` gates whether those styles actually render, so flipping a setting never requires re-walking the DOM.
- **PDF support is manual-open only, by design.** MV3 extensions can't silently register as Chrome's default PDF handler the way the old `mimeHandlerPrivate` API allowed — the realistic options were auto-intercepting every PDF navigation (needs `declarativeNetRequest` + broad host permissions) or manual open (file picker / "reopen this PDF" button, no new permissions). This project chose manual-open; the viewer is reached only via `chrome.tabs.create` from `popup.js`, never via navigation interception.
- **The PDF viewer is Mozilla's own prebuilt PDF.js reference viewer** (`pdf-viewer/vendor/web/viewer.html` + `viewer.mjs`), not a hand-built one. A hand-rolled render pipeline was tried first (single-page, then continuous-scroll) and broke twice — both times because it was re-implementing things PDF.js's own viewer already does correctly (proper virtualized continuous scroll, zoom, and a pixel-correct native highlight annotation tool). Don't re-attempt a custom render pipeline; if the stock viewer is ever swapped for a newer PDF.js release, re-vendor `web/` + `build/` wholesale (see `vendor/README.txt`) rather than cherry-picking files — its internal `cMapUrl`/`standardFontDataUrl`/`wasmUrl`/`workerSrc` defaults are relative paths (`../web/...`, `../build/...`) that depend on the original folder layout being preserved exactly.
- **`pdf-viewer/bridge.js` layers our features on top of the stock viewer** — translate-on-click/hover/selection (ported from `content/content-script.js`; not shared/injected, since content scripts don't run on the extension's own pages and `content-script.js` is a classic script while `bridge.js` is an ES module) and the handoff-loading/content-hash logic. It does **not** touch rendering, scrolling, zoom, or highlighting — those are entirely the stock viewer's job. Highlighting uses PDF.js's own native annotation tool (its own toolbar), not a custom feature — nothing in this extension writes or reads PDF annotation data.
  - **The viewer URL must carry an empty `file=` param** (`viewer.html?file=&handoff=<token>`, built in `popup.js`) — otherwise the stock build opens its bundled sample PDF, which isn't vendored, so the request 404s. `viewer.mjs` reads `file = params.get("file") ?? AppOptions.get("defaultUrl")`, and `??` only falls through on **null/undefined**, so an empty-string `file` means `defaultUrl` is never consulted at all; `file` then fails the falsy guards in `validateFileURL()` and `if (file)`, so nothing is opened and nothing is fetched. No timing involved. `bridge.js` also calls `AppOptions.set("defaultUrl", "")` at module top level, but that is a **fallback for tabs opened with an older URL, not the fix** — two earlier attempts at it failed. Setting it from the `webviewerloaded` event never runs at all: `viewer.mjs` ends with `if (document.readyState === "interactive" || … "complete") webViewerLoad()`, and per the HTML spec's "the end" `readyState` is `"interactive"` *before* deferred/module scripts run, so `viewer.mjs` dispatches the event and calls `run()` during its own evaluation, and `bridge.js` — whose `<script>` comes after it — is always too late. Moving it to module top level is **also** not sufficient: whether `run()` reaches the `defaultUrl` read before or after `bridge.js` executes depends on how many real async boundaries `initialize()` crosses, which is a race — and one it lost in practice. The `webviewerloaded` listener is kept as insurance against a future PDF.js release deferring `webViewerLoad()`. The symptom was invisible whenever the handoff succeeded, because our own `open()` superseded the doomed sample-PDF load — it only surfaced as a confusing `compressed.tracemonkey-pldi-09.pdf` fetch error once a handoff went missing.
  - **A missing/expired handoff is a normal state, not a crash**, and `loadHandoff()` must say so on screen (`showViewerError()`), not just in the console: records are swept after 30 minutes, and reloading the extension re-navigates any open viewer tab to its original `?handoff=` URL, so landing here is routine. The panel is styled in `content/popup.css` (already linked into `viewer.html`) and builds its DOM node-by-node — the vendored `viewer.html` ships a strict CSP (`style-src 'self'`), under which CSSOM and classes are fine but a `style` attribute is not.
  - Load order matters: `viewer.mjs` assigns `window.PDFViewerApplication`/`PDFViewerApplicationOptions` at module top level, and `bridge.js`'s `<script>` tag comes after it in `viewer.html` — reversing that order would leave those globals undefined when `bridge.js` runs.
- **PDF vocab is keyed by content hash, not URL**: `pdf:<sha256hex>`, computed in `bridge.js` from the PDF's raw bytes. This flows through the *existing* `vocab[url]`/`cards`/`saveWord()` machinery unchanged (`lib/normalize-url.js#normalizeUrl()` passes a `pdf:...` key through untouched — verified, it's a non-special URL scheme with no hostname/trailing-slash to normalize) — the only change needed was making `saveWord()`'s `SAVE_WORD` handler respect an explicit `entry.url` instead of always overwriting it with `sender.tab.url` (which for a viewer tab would be its own `chrome-extension://.../viewer.html?handoff=...` address).
- **A hand-made collection is a vocab bucket keyed `collection:<uuid>`** — the same trick `pdf:<hash>` plays, and `normalizeUrl()` passes both through untouched (a non-special scheme with no hostname or trailing slash to normalise), so cards, search, export, rename and delete need no special-casing. Two rules it *does* need: `labelForWorkbook()` has a `collection:` branch, and **`deleteEntry()` must not delete an emptied collection** the way it deletes an emptied page workbook — a page bucket exists only because something was saved from it, whereas a collection was created deliberately and has to survive being emptied. Only `deleteWorkbook()` removes one.
- **The side panel re-renders from `chrome.storage.onChanged`, not from its own save calls.** Saving happens in the page, the PDF viewer or the Conjugation tab — never in the list that has to show it — so `handleVocabChange()` watches the `vocab` key and is the single owner of "a word was added": it re-renders, selects the workbook the word landed in, clears a search filter *only* if that filter would hide it, and plays the arrival animation on the new card. `onChanged` supplies both `oldValue` and `newValue`, so the added entry is identified by diffing ids rather than guessed from a timestamp. Save paths inside the panel deliberately do **not** re-render themselves — doing so raced the listener and dropped the animation. Rename is the exception that still renders directly: it writes `workbookNames`, not `vocab`, so the listener never fires for it.
- **Words can be typed straight in** (`#addWordForm` in the side panel), not only saved from a page. It reuses `SAVE_WORD` with an explicit `entry.url` (the destination bucket) and only calls `TRANSLATE` when the user left the translation blank — the response's own `sourceLang` sets the direction, so typing an English word to learn its French works as well as the reverse.
- **Each `vocab[url]` bucket is a "workbook"** in the side panel's UI (one per page/PDF, plus an "All Words" selection that flattens every workbook's entries into one list) — `sidepanel.js`'s `deleteWorkbook()` is the one place that removes a bucket wholesale, and it must clean up every place that references it: strip the deleted occurrences out of `cards[lemma].occurrenceIds` (dropping any card left with none), and drop `workbookNames[url]` too. Deleting a single entry (`deleteEntry()`) does the `cards` part already; adding a new per-workbook side-effect means checking both functions.
- **Conversation practice (`lib/practice-panel.js`) runs entirely in the side panel** — `webkitSpeechRecognition`/`speechSynthesis` are window-context UI APIs the service worker can't run, so the live session state machine (parse → classify → alternating turns → summary) lives in the panel, with session state deliberately ephemeral (module memory, nothing persisted). Translations still route through `TRANSLATE` messages — one per dialogue line, whose `sourceLang` classifies the line (fr vs en) and whose `translation` doubles as the Mode B reference / display gloss. Same shared-module shape as `settings-panel.js`: exported `initPracticePanel()` with an idempotent listener guard, caller-provided element IDs.
  - **Three modes, inferred from the parsed lines**: A (all French — alternating read-aloud turns), B (mixed — the app reads French, the user speaks the English lines in French), C (all English — every line is the user's to translate aloud, nothing is read to them). C is B with no app lines left, so it shares B's lenient threshold and its "suggested translation" framing; `isTranslateTurn()` (`line.lang === "en"`) is the single test for "the user must produce French here", and it gates scoring leniency, the reference label, and — importantly — never revealing the reference mid-attempt.
  - **Recognition runs `continuous`, and the panel decides when a turn ends** — on ~1.8s of silence, the ✓ Done button, or a hard cap. With `continuous = false` Chrome ends the session at its first final result, which for a spoken sentence is often just the opening word, so the line was scored and failed before the user finished saying it. `e.results` accumulates across the turn, so the transcript is rebuilt from the whole array on each event, not appended to.
  - **Scoring is phonetic, not orthographic** — `lib/fuzzy-match.js#pronunciationScore()` over `phoneticKey()`, a lossy French grapheme→sound folding. Character-Levenshtein (the old `similarity`) marks a learner wrong for spellings French pronounces identically (`parler`/`parlé`/`parlez`), which made the feedback far harsher than the speaking actually was. The folding deliberately over-merges — a false pass costs a learner much less than a false fail. `similarity`/`wordDiff`/`alignWords` are all still exported unchanged; the new functions were added beside them.
  - **The mic level meter is a second, parallel `getUserMedia` stream**, purely decorative and entirely best-effort (any failure just hides the canvas; recognition never waits on it). It exists because `SpeechRecognition` emits nothing at all until it has decoded words, so a wrong input device is indistinguishable from a user who hasn't spoken — which is exactly how it was first hit. Chrome lets the two captures coexist; Web Speech does its own.
- **Mic permission comes from a one-time grant page** (`permission/grant-mic.html`, opened in a tab via `chrome.tabs.create`) — the side panel can't show Chrome's mic prompt itself, but once `getUserMedia({audio:true})` is granted there, recognition works panel-side (same extension origin). No manifest permission involved: `audioCapture` is a Chrome-Apps permission, not an extension one — don't add it. The panel surfaces this as a **modal gate on entering Practice** (`#micModal`), not a button living in the controls — it's one-time setup, so it shouldn't hold permanent space. "Not now" suppresses it for the panel's lifetime, but a real `not-allowed` error overrides that and re-raises it.
- **Additive message contract** — add fields, don't rename or remove.
- **A tour step's `body` must be cloned, not appended.** `para()` returns a DocumentFragment and appending one MOVES its children out, leaving it empty — and step bodies are built once, at module load. `lib/tour.js` appends `body.cloneNode(true)`; without it a step rendered its text the first time only, so going Back and forward (or replaying) left every visited step as a bare heading.
- **The workbook tour is opt-in, never a consequence.** The welcome tour's bubble buttons open the side panel mid-flight, so the panel must not launch its own tour off the back of that: `maybeRunPanelTour()` bails while `welcomeTourRunning` is set, and the tour is reached deliberately — "Tour the workbook" on the welcome page (via a `panelTourRequest` key, which runs it even if already seen) or by opening the panel later. There is no `chrome.sidePanel.close()`; `closeWorkbook()` disables the panel for the tab and re-enables it in a `finally`, since leaving it disabled would make the workbook unopenable in that tab.
- **The tutorial's buttons do the real thing, and it cleans up after itself.** The welcome page's Conjugate/Workbook/Save genuinely conjugate, genuinely open the panel and genuinely save — a tutorial that mimes its features teaches the mime. Because that means the *result* lands in the side panel, which is a different document that `lib/tour.js` cannot dim, the welcome page writes a `tourSpotlight` note to storage and the panel runs a one-step spotlight of its own when it sees one (fresh-and-once guards mirror `handleIntent`'s). The save goes to a dedicated `collection:tutorial` bucket and `endTour()` removes it — that reconciles "buttons should work" with "tutorial words must not litter the workbook", and it runs on every exit path, not just Finish. `SAVE_WORD` returns `id`/`url` so the cleanup can be scoped to exactly what the tutorial wrote.
- **`--fla-overlay` is the surface for anything floating above the page** — tour callouts and popup menus (`.ctx-menu`, the export menu). Deliberately *not* `--fla-card`: a callout drawn in the same colour as the cards behind it doesn't read as sitting on top of them. `check-contrast.js` holds it to a separation floor against `--fla-card` as well as the usual text pairings.
- **Tour callouts are one component, so they must be one size.** A centred step (`target: null`) once set its own width, which is what made otherwise-identical steps look like two different things; `.fla-tour--centred` now controls position only. `lib/tour.js` exports `para()` so every tour writes bodies as paragraphs rather than one dense block, and `advanceTour()` so a step can be driven by something the user did on the page — the welcome tour's "click any word" step has `hideNext: true` and moves on when a word is actually clicked, instead of offering a button that asks the user to confirm they did it.
- **One entry per word per workbook, and one row per word in "All Words".** `saveWord()` dedupes within a bucket on `cardId` (the lemma), not the surface form — "parle" and "parler" are already one card, so listing both in one collection is the same word twice. A repeat save *refreshes* the existing entry (newest translation/context win, the `id` is kept so `cards[].occurrenceIds` stays valid) and returns `duplicate: true` so callers can say "already saved" rather than implying a new row appeared. The same word deliberately kept in two different collections is still allowed — that's the point of collections — but `allWordsEntries()` in `sidepanel.js` collapses it to one row for the flattened view, the rail's count, and both exports, so it can't look like a duplicate there.
- **The reading level is pushed, not polled.** `content/annotator.js` sends `PAGE_LEVEL` whenever its CEFR estimate changes; the service worker files it under `pageLevels[tabId]` (only the worker knows the sender's tab id) and the readers follow that key via `chrome.storage.onChanged`. `GET_PAGE_LEVEL` is kept as a fallback but is no longer the main path: both callers asked exactly once, and scanning is chunked across idle callbacks with a debounced recompute, so that single question reliably arrived *before* any level existed — the label said "Analyzing…" forever. `chrome.tabs.sendMessage` is also not dependable here, since this extension requests no host permissions.
- **Frequency dimming and cognate highlighting are retired, not deleted.** The toggles, the `.fla-dim`/`.fla-cognate` classes, their CSS and the `config` keys are gone. What remains on purpose: `data/cognates.json` is still bundled, `LOOKUP_WORDS` still returns `cognates` and `freqRank`, and `freqRank` still feeds the CEFR estimate — so reviving either is a UI change, not a data one. Don't "tidy" the data or the message fields away.
- **A saved word's context sentence is measured with a probe Range, never by identity-matching text nodes.** `getContextSentence()` (duplicated in `content/content-script.js` and `pdf-viewer/bridge.js`) walks no trees: it does `selectNodeContents(container)` + `setEnd(node, offset)` and takes `.toString().length`. The earlier TreeWalker version only ever matched **text** nodes, so any Range anchored to an **element** — which `Selection` produces routinely at block boundaries — silently fell through to a fallback that returned the container's first 300 characters. On an `<article>`, or the PDF viewer's per-page text layer, that saved an unrelated sentence from elsewhere on the page as "the sentence you met this word in". If the probe ever fails, fall back to the word's **own** text node, never to a slice of the container: wrong context reads as correct and is worse than terse context.
- **The first-run tutorial is a spotlight tour, and it can only ever cover surfaces we own.** `lib/tour.js` dims the page with one cutout element (`box-shadow: 0 0 0 9999px <scrim>`, so the spotlit element keeps its true colours and there's no second dimming layer to keep in sync) and anchors a callout to a target. Same shared-module shape as `settings-panel.js`/`theme-mode.js`. Used by `welcome/welcome.js` and `sidepanel/sidepanel.js` — both regular extension pages, so it's a real shared module.
  - **Browser chrome cannot be spotlighted**: the toolbar icon, the pin menu and the side panel's outer frame are in no DOM we control, so `welcome.html` *draws* a toolbar (`#toolbarMock`) and points at that instead. Likewise `chrome.sidePanel.open()` needs a user gesture — the tour's own button click supplies it; nothing can auto-open the panel.
  - **The welcome page reproduces the in-page experience rather than running it.** Content scripts don't run on `chrome-extension://` pages, so `welcome.js` links the real `content/popup.css` and emits the real `.fla-word--*`/`.fla-bubble` markup, sending genuine `TRANSLATE`/`SAVE_WORD` messages (both work from an extension page — the handlers only use `sender.tab` optionally). It falls back to a canned gloss when on-device translation is unavailable, so the tutorial never dead-ends. It also listens for the `TRANSLATE_STATUS` broadcast the way `pdf-viewer/bridge.js` does, which turns the one-time language-pack download from a mystery stall into an explained one.
  - Because `content/popup.css` themes the bubble off `.fla-theme-dark`/`.fla-theme-light` (what `annotator.js` sets on host pages) and not off `data-theme`, `welcome.js` mirrors the resolved theme onto **both** — otherwise an explicit Light/Dark choice themes the page and leaves the demo bubble behind.
  - **`welcomeOpenedAt` (set by the worker) and `welcomeSeenAt` (set by the page) are deliberately different fields.** If `onInstalled` marked the tour seen, opening the tab would suppress the very tour it opened the tab for. The worker's open is also guarded on stored state, not just `details.reason` — reloading an unpacked extension can re-fire `reason: "install"`, which would otherwise spawn a welcome tab on every dev reload.
  - **A step whose target has no box centres instead of throwing.** On a genuine first run the side panel's lists are empty, so panel-tour copy must read correctly with nothing saved. The tour re-measures on resize *and* via a `ResizeObserver` — the side panel is user-resizable, so the viewport changes without a `resize` event.
  - Keep the tour off anything unbuilt. `srs.js` is an interval table only, `GET_DUE_REVIEWS`/`RECORD_REVIEW` have no handler, `gameState`/`config.gamification` are never read or written, and nothing displays saved `verbs` — README's "Review / Progress tabs", streaks and word counts do not exist.
- **One design system, "The Library at Dusk", lives in `lib/theme.css`** — paper-cream surfaces, near-black indigo as the single filled-button colour, sage for "correct"/affirmative, muted terracotta for near-misses, and a serif-forward hierarchy (EB Garamond for French, Public Sans for chrome). Every regular extension page links it *before* its own stylesheet (`popup/`, `sidepanel/`, `permission/`), and each page's CSS then uses only `--fla-*` tokens — no raw hex. Ported from the project's Stitch design (project `7499537201026743765`); the brief that governs it is that project's "Product Brief & Design Specification" screen.
  - **`content/popup.css` keeps a scoped duplicate of the tokens and `@font-face` rules, and the two must be kept in sync.** A content script must never define custom properties at `:root` — that leaks the whole palette onto the host page — so the bubble declares its tokens on `.fla-bubble` itself. Its `@font-face` families are deliberately named `L auxiliaire Garamond`/`L auxiliaire Sans` rather than the real font names, so a host page that already uses EB Garamond can't have its own faces collide with ours.
  - **The typographic rule is: French is serif, UI chrome is sans, English glosses are italic sans.** That's what makes a saved word, a bubble's source text, and a practice line read as *content* rather than as interface. It's applied purely in CSS — no JS builds any of these DOMs differently than before.
  - **Webfonts are bundled in `fonts/` (latin subset, ~147KB total), never linked from Google Fonts** — a content script's stylesheet is subject to the *host page's* CSP, so a remote font would silently fail on plenty of real sites. They're listed in `web_accessible_resources` for `<all_urls>` so the in-page bubble can reach them; every stack still names a real system fallback (Georgia / system sans), so a CSP that blocks even the extension-origin font degrades without a layout shift. See `fonts/README.txt` to refresh them.
  - **`node scripts/check-contrast.js` guards both of the above** and must stay passing. It measures every text/surface token pairing the UI actually renders, in *both* schemes, and diffs the bubble's token copy against `lib/theme.css`. Two rules it encodes are easy to get wrong: small letterspaced caps (the tabs, the `fr`/`en` chips) are held to **6:1**, not WCAG AA's 4.5:1, because that floor is calibrated for normal-weight body text; and **nothing may use `opacity` to make text quiet** — opacity compounds against the surface and silently drops an already-faint ink under 3:1, which is how the first dark palette became unreadable. Use a lighter ink token instead.
  - **Dark mode is not an inversion of the light ramp.** Dark surfaces need visibly more separation to read as the same hierarchy, so the dark inks sit lighter than a mechanical flip would put them, and `--fla-bg`/`--fla-card` are lifted off pure black. `--fla-heading` exists precisely because `--fla-primary` can't do both jobs in dark: a fill light enough to carry black button text is far too washed out to set a word in.
  - **Light/dark is a user choice, not just an OS one** — `config.themeMode` is `"system"` (default, and what an absent value means) / `"light"` / `"dark"`. `lib/theme-mode.js` is the shared module that owns it: it stamps `data-theme` on `<html>`, which `lib/theme.css` keys off, and its `initThemeMode(onChange)` follows `chrome.storage.onChanged` so every open surface reacts to a change made anywhere. Two entry points write the same key — the Settings tab's "Appearance" select (via `lib/settings-panel.js`, so the popup gets it too) and the workbook rail's sun/moon button (`#themeToggle`, side panel only). The button always commits to an *explicit* mode, including from `"system"`; only the select can go back to following the OS.
    - **The dark values are written out twice per file, and that duplication is checked, not trusted.** A media query and a plain selector can't be combined into one rule and there's no build step, so `lib/theme.css` carries `@media (prefers-color-scheme: dark) :root:not([data-theme="light"])` *and* `:root[data-theme="dark"]`, and `content/popup.css` carries the `html:not(.fla-theme-light) .fla-bubble` / `html.fla-theme-dark .fla-bubble` pair. The `:not()` guards are what make an explicit "Light" choice survive a dark OS. `check-contrast.js` asserts all copies are identical.
    - The bubble follows the same setting through `content/annotator.js`, which mirrors `config.themeMode` onto the host page's `<html>` as `.fla-theme-dark`/`.fla-theme-light` — the same `applyConfigToDocument()` that already handles the reading-aid classes, so it inherits the live-across-every-tab behaviour for free.
  - Reading-aid gender colours are **not** part of this palette — they're user-configurable and stored in `config.colorCoding`, so they stay where they are.

## Message contract

Request → response:
- `TRANSLATE` `{ text, contextSentence? }` → `{ source, translation, sourceLang, targetLang }`
- `SAVE_WORD` `{ entry }` → `{ ok, count }` — `entry.url` is used as-is if the caller provides one (e.g. `pdf-viewer/bridge.js`'s `pdf:<hash>` key), only falling back to `sender.tab?.url` when absent (regular content-script saves never set it)
- `SAVE_VERB` `{ table }` → `{ ok }`
- `CONJUGATE` `{ verb }` → `{ ok, table } | { error }`
- `OPEN_SIDEPANEL` `{ view, verb?, text? }` → `{ ok }` — `verb` rides along for `view: "conjugation"`, `text` (the selected dialogue) for `view: "practice"`. Delivered to the panel via the `sidepanelIntent` storage key, which the panel consumes both at load (`checkIntent()`) and live via `chrome.storage.onChanged` (so an already-open panel reacts too)
- `SET_HOVER_MODE` `{ enabled }` → `{ ok }` — click-to-translate is always on (no toggle/message for it); hover-dwell is the only optional mode, additive on top of click
- `READ_SELECTION` `{ lang }` → `{ ok }`
- `GET_DUE_REVIEWS` `{}` → `{ items }` — **Phase 3, not yet wired** (no service-worker handler yet; `cards` now has the `dueAt` field this will scan)
- `RECORD_REVIEW` `{ id, correct }` → `{ ok, nextDue }` — **Phase 3, not yet wired** (`background/srs.js` currently only has the box→interval table; promote/demote-on-review logic still to come)
- `LOOKUP_WORDS` `{ words }` → `{ entries: {[word]: {lemma,pos,gender,number,freqRank}|null}, cognates: {[word]: string} }` — batched lexicon + cognate lookup, one call per `content/annotator.js` scan pass. Also sent for a single word by the in-page bubble, to label a noun's gender. `cognates` and `freqRank` are still returned though nothing renders them (see the retired-aids note in Conventions)
- `GET_SELECTION` `{}` → `{ text }` — reads the active tab's selection from a surface that can see it (the popup can't read the page itself). **No caller sends this today** — the popup's "🎙 Practice selected text" button was removed; practice is reached from the in-page bubble's 🎙 button and the panel's Practice tab instead. Both listeners are kept: the contract is additive, and this is the only way for an extension page to read a tab's selection. Answered by `content/content-script.js` via `chrome.tabs.sendMessage`, and by `pdf-viewer/bridge.js` via a `chrome.runtime.sendMessage` broadcast fallback (it's an extension page, not a content script). **A listener with no selection must not reply at all** — both delivery paths fan out to multiple receivers (every frame in the tab; every open viewer tab) and the first `sendResponse` wins, so an empty answer from an unrelated frame would beat the real one. No responder means the send rejects, which the caller reads as "nothing selected"
- `GET_PAGE_LEVEL` `{}` → `{ level: "A1".."C2"|null, pending? }` — sent **popup → content script directly** (not background-routed; `annotator.js` already holds the per-page data from its own scans). Frequency-rank banding only — v1 deliberately does not factor in the user's known-vocabulary/`cards` data, to keep the metric simple and independent of review history

## MV3 constraints (silent-bug traps)

- No inline `<script>` in HTML.
- Service worker can die between events — persist to `chrome.storage`, don't hold in-memory state.
- Content script runs on `<all_urls>` — be defensive, don't break host pages.
- `webkitSpeechRecognition` is Chrome-only (Firefox port would lose Practice tab).
- `Translator.*`/`LanguageDetector.*` don't work in Web Workers — a service worker is one, so it can't call them directly. That's why `background/offscreen.js` exists: it's spawned via `chrome.offscreen.createDocument` and relayed through, since offscreen documents have a real window context. Requires Chrome 138+.
- `chrome.runtime.sendMessage` fans out to every *other* extension context (the sender's own exact listener never receives its own broadcast) — with three contexts now sharing one bus (service worker, offscreen doc, content scripts), a message meant for one will still reach the others' listeners. Filter by `msg.type` before acting, and don't assume "my listener didn't fire" means "nothing else did either."

## Data bundles (in `data/`)

- `verbs/<letter>.json` + `lemmas/<letter>.json` — ~7000 French verb conjugations, sharded by normalized first letter so a lookup only loads ~1/26th of the data. Generated from Verbiste XML via `scripts/build-verbiste.js`.
- `lexicon/<letter>.json` — Lexique.org derived (source: `data/Lexique4/Lexique4.tsv`), top 30k surface forms with `{ lemma, pos, gender, number, freqRank }`, same first-letter sharding scheme. Generated via `scripts/build-lexicon.js`. `pos` is the raw Lexique `Cgram` code; homographs (same spelling, multiple grammatical readings — e.g. "ferme" as VER/ADV/ADJ/NOM) collapse to one entry keyed by the reading with the highest word-form frequency, but ranked by the spelling's aggregate frequency across all readings — see the script's header comment for the full rationale.
- `cognates.json` — hand-curated English-French cognate map (not scripted — there's no reliable way to derive true cognates vs. false friends from frequency/POS data alone), `{ frenchWord: englishCognate }`

`scripts/shard-writer.js` holds the shared `normalize()`/`shardKeyOf()`/`writeSharded()` build-time helpers (CommonJS, used by both build scripts). `background/conjugation.js` and `background/lexicon.js` each keep their own small runtime copy of `normalize`/`shardKeyOf` (different module system — ES modules in the service worker) — all copies must match exactly, or a word looks up a shard that was never built for it.

`pdf-viewer/vendor/` is a vendored third-party application (Mozilla's PDF.js **reference viewer**, Apache-2.0), not generated data — see `vendor/README.txt` for the exact release/files taken and how to upgrade. Unlike an earlier version of this project (which vendored only the display API and hand-built a minimal page against it), the **whole** `web/` + `build/` viewer app is vendored — `viewer.html`/`viewer.mjs`/`viewer.css`, its images/locale(`en-US` only)/`standard_fonts`/`wasm`/`cmaps` assets, and `build/pdf.mjs`/`pdf.worker.mjs`. This project's own code only adds `pdf-viewer/bridge.js` (translate/save/handoff-loading) plus two `<script>`/`<link>` tags inserted into the vendored `viewer.html` — everything else is upstream, unmodified.
